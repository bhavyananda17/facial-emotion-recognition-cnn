# Facial Emotion Recognition CNN: a reproduction

A clean, reproducible re-implementation of

> R. Raj and I. Demirkol, "An improved facial emotion recognition system using convolutional neural network for the optimization of human robot interaction", *Scientific Reports* 15:38940 (2025). [doi:10.1038/s41598-025-22835-0](https://doi.org/10.1038/s41598-025-22835-0)

The three official Keras notebooks ([raj91ravi/Facial-Emotion-Recognition](https://github.com/raj91ravi/Facial-Emotion-Recognition)) are treated as the source of truth for hyperparameters. The paper provides context. The code here is a rewrite, not a copy of the notebooks.

The model is trained on **CK+**, **FER2013** and **RAF-DB** under two protocols:

| Protocol | Validation data used for early stopping / LR schedule | Purpose |
|---|---|---|
| `paper` | the **test set** (exactly as in the notebooks) | numbers comparable to the paper |
| `clean` | a held-out 10% of the training set; test set used once at the end | an unbiased estimate |

## Headline results

| Dataset | Paper reports | Mine, paper protocol | Mine, clean protocol |
|---|---|---|---|
| CK+ | 95% | 94.4% | 90.9% (4-seed mean 94.1 ± 2.6%) |
| RAF-DB | 83% | 83.0% | 83.2% |
| FER2013 | 64% | 65.3% | 64.8% |

The paper's accuracies **reproduce** (within 1.3 points), and, surprisingly, evaluating without test-set leakage **does not measurably change them**. The findings that do matter are mislabelled per-class results in the original, near-duplicate frames in the CK+ split, and a learning-rate setting that freezes training. Full table and discussion: [`results/summary.md`](results/summary.md) (generated by `scripts/make_summary.py`).

### Environment notes

- **TensorFlow 2.18** is the version used in the paper (Table 3), and `tensorflow-metal 1.2.0` is the Metal plugin release built for it.
- **Keras is pinned to 3.8.0.** TF 2.18 only requires `keras>=3.5`, so pip would otherwise install the newest Keras (3.15 at the time of writing). Pinning keeps the environment close to what TF 2.18 was released with.
- On the Metal GPU, the `SeparableConv2D` layers (FER2013, RAF-DB) run slower than `Conv2D` at 48×48. At 100×100 the GPU is still faster than the CPU (131 vs 181 ms/step in a synthetic benchmark).

## Data

Datasets come from Kaggle (the links in the paper's Data availability section) and are git-ignored. Put your Kaggle credentials in `~/.kaggle/kaggle.json` or `~/.kaggle/access_token`, then:

```bash
python -m src.data --config configs/ck.yaml --download   # fetch into data/ck/raw
python -m src.data --config configs/ck.yaml --split      # CK+ only: seeded 80/20 split
python -m src.data --config configs/ck.yaml --inspect    # image counts and class order
```

FER2013 and RAF-DB already ship with train/test folders, so they only need `--download`.

### CK+ as downloaded

981 images, 48×48 grayscale PNGs, 7 classes (anger, contempt, disgust, fear, happy, sadness, surprise; no neutral). File names are `S<subject>_<sequence>_<frame>.png` and **every sequence contributes exactly 3 consecutive frames**.

| Split (seed 42) | Images |
|---|---|
| train | 783 (708 after Keras holds out 10% for `validation_split`) |
| test | 198 |
| clean-protocol validation | 75 |

These counts equal the ones in the official notebook's output (708 / 198) and the paper's Table 2 (783 / 198).

**Leakage inside the CK+ split.** The notebook splits *images*, not subjects or sequences. With our seeded split, **180 of the 198 test images (91%) have a sibling frame from the same sequence in the training folder**, and 195 of 198 (98%) come from a subject who also appears in training (`results/ck/split_report.json`). The clean protocol fixes the test-set-as-validation problem but not this near-duplicate overlap, so CK+ accuracy stays optimistic under both protocols.

### How the generators are built (`src/data.py`)

- Both protocols train on the same augmented training subset (`validation_split=0.1`, `subset='training'`), exactly like the notebooks, so the 10% held-out slice is never trained on.
- `paper`: that slice is ignored and the **test set** is the monitored validation data.
- `clean`: the held-out slice (`subset='validation'`, rescale only, a stratified 10% of every class) is monitored instead. The test set is only used for the final evaluation.
- `check_class_order` stops the run if Keras' class order differs from the config.

## Training and evaluation

```bash
python -m src.model                                              # check parameter counts vs the notebooks
python -m src.train --config configs/ck.yaml --protocol paper    # train + evaluate, writes results/ck/paper/
python -m src.evaluate --config configs/ck.yaml --protocol paper # re-evaluate a saved model
```

Each run writes to `results/<dataset>/<protocol>/`: `training_curves.png`, `confusion_matrix_counts.png`, `confusion_matrix_normalised.png`, `roc_curves.png` (one-vs-rest, per-class AUC), `sample_predictions.png` (green = correct, red = wrong), `classification_report.{txt,csv,json}`, `predictions.csv`, `metrics.json`, `model_summary.txt`, `history.csv`, `train.log` and `run_info.json` (parameters, training time, epochs, device, git commit). Models are saved to `models/<dataset>_<protocol>.keras`.

`src/model.py` reproduces the notebooks' parameter counts exactly: 7,057,351 (CK+), 2,907,984 (FER2013), 9,985,872 (RAF-DB).

## Results

### CK+, paper protocol (seed 42, Apple M5 Pro GPU)

| | This run | Paper |
|---|---|---|
| Test accuracy | **94.4%** (187/198) | 95% |
| Macro F1 / macro AUC | 0.924 / 0.998 | n/a |
| Training time | 2.2 min (100 epochs, ~1.3 s/epoch) | n/a |

Weakest class is Sadness (recall 0.71; 4 of 17 predicted as Anger). Details are in `results/ck/paper/`.

Things worth knowing when reading the curves:

- **Early stopping never fired.** All 100 epochs ran. The best epoch (87) was chosen by the *test* loss, which is what `restore_best_weights` restores.
- **The learning rate collapses.** `ReduceLROnPlateau(factor=0.001)` multiplies the rate by 0.001, not 0.1: it falls from 1e-3 to 1e-6 at epoch 38, 1e-9 at epoch 82 and 1e-12 at epoch 97, so the model is effectively frozen after epoch ~40. This matches the notebook's own log (its learning rate also reaches 1e-6).
- **Test accuracy (94%) is above training accuracy (88%).** Training accuracy is measured with dropout and augmentation switched on, and the monitored test images are near-duplicates of training frames (see the CK+ leakage note above).

### RAF-DB, paper protocol (seed 42, Apple M5 Pro GPU)

| | This run | Paper |
|---|---|---|
| Test accuracy | **83.0%** (2,546/3,068) | 83% |
| Macro F1 / macro AUC | 0.748 / 0.967 | n/a |
| Training time | 80.9 min (100 epochs, ~49 s/epoch) | n/a |

All 100 epochs ran (early stopping did not fire); the learning rate dropped to 1e-6 at epoch 45 and 1e-9 at epoch 96, and the best epoch by test loss was 99. Happy is easiest (recall 0.90); **Disgust (0.47) and Fear (0.55) are hardest**, and they are also the two smallest classes (717 and 281 training images against 4,772 for Happy). Disgust is most often mistaken for Neutral (21%) and Sad (14%).

**Label coding check.** The RAF-DB folders are named `1`–`7`. Their sizes (1,619 / 355 / 877 / 5,957 / 2,460 / 867 / 3,204 images over train + test) match the published RAF-DB class totals, and sample faces from each folder agree (`results/rafdb/label_check.png`), giving 1 Surprise, 2 Fear, 3 Disgust, 4 Happy, 5 Sad, 6 Angry, 7 Neutral. The official notebook labels its plots Angry, Disgust, Fear, Happy, Sad, Surprise, Neutral, which is wrong for folders 1, 2, 3 and 6. Accuracy is unaffected; the notebook's per-class plots and tables are mislabelled. This repo uses the correct names everywhere.

### FER2013, paper protocol (seed 42, Apple M5 Pro GPU)

| | This run | Paper |
|---|---|---|
| Test accuracy | **65.3%** (4,688/7,178) | 64% |
| Macro F1 / macro AUC | 0.613 / 0.910 | n/a |
| Training time | 98.8 min (100 epochs, ~59 s/epoch) | n/a |

All 100 epochs ran; the learning rate dropped to 1e-6 at epoch 46 and the best epoch by test loss was the last one. Happy (recall 0.87), Surprise (0.80) and Neutral (0.73) are easiest. **Fear (0.36) and Disgust (0.40) are hardest**; Disgust has only 436 training images, and 39% of Disgust test images are predicted as Angry. FER2013's labels are known to be noisy, so a ceiling in the 60s to low 70s is normal and 65% is not a model failure.

**Independent evidence for the label mix-up in the paper's Table 4.** The notebook labels the sorted classes Angry, Disgust, Fear, Happy, Sad, Surprise, Neutral, but the real order is Angry, Disgust, Fear, Happy, **Neutral, Sad, Surprise**. If that is what happened, the paper's rows for Sad, Surprise and Neutral should belong to my Neutral, Sad and Surprise. They do (precision / recall):

| Paper's row label | Paper (P / R) | My true class | Mine (P / R) |
|---|---|---|---|
| Sadness | 0.52 / 0.73 | **Neutral** | 0.521 / 0.732 |
| Surprise | 0.56 / 0.44 | **Sad** | 0.582 / 0.455 |
| Neutral | 0.74 / 0.80 | **Surprise** | 0.740 / 0.800 |

The unaffected rows also agree (Happy 0.86 / 0.87 vs 0.862 / 0.874; Angry 0.53 / 0.60 vs 0.563 / 0.620; Fear 0.55 / 0.34 vs 0.557 / 0.356). The paper's accuracy is correct but its per-class labels are shifted.

### CK+, clean protocol vs paper protocol (seed 42)

Same model, same 708 training images, same seed, same test set. The only change is what early stopping and the learning-rate schedule watch: the **test set** (paper) or a **75-image slice held out from training** (clean).

| | Paper protocol | Clean protocol |
|---|---|---|
| Test accuracy | **94.4%** (187/198) | **90.9%** (180/198) |
| Macro F1 | 0.924 | 0.865 |
| Epochs run / best epoch | 100 / 87 | 56 (early stopping fired) / 31 |
| Training time | 2.2 min | 1.2 min |

At seed 42 the clean protocol misclassifies 7 more test images. **That single gap turned out not to be representative** (next section).

#### Is the gap real? Four training seeds

`python -m src.train ... --seed N` changes only the training randomness (weights, augmentation, batch order); the CK+ split stays fixed at seed 42, so every run is scored on the same 198 images. `python scripts/summarize_seeds.py ck` writes `results/ck/multi_seed.md`.

| Seed | Paper protocol | Clean protocol | Gap (paper − clean) |
|---|---|---|---|
| 1 | 94.4% | 96.0% | −1.5 pts |
| 2 | 94.9% | 92.9% | +2.0 pts |
| 3 | 95.5% | 96.5% | −1.0 pts |
| 42 (headline) | 94.4% | 90.9% | +3.5 pts |
| **Mean ± std** | **94.8 ± 0.5%** | **94.1 ± 2.6%** | **+0.8 ± 2.4 pts** |

The paper protocol came out ahead in only 2 of 4 seeds, and the mean gap (+0.8) is smaller than its own spread (2.4). **On CK+ we cannot detect an effect of using the test set for early stopping**: the signal is smaller than the noise from the random seed. Two things make this plausible rather than surprising. (1) The paper-protocol results are very stable (std 0.5) and the clean ones are noisy (std 2.6), because the clean run chooses its stopping point from a validation slice of only 75 images. (2) The test set itself is leaky in a way neither protocol fixes: 91% of CK+ test images have a sibling frame in training, so the test set is easy for both. The leakage in the paper's *protocol* is real in principle, but on this dataset and model it does not measurably change the reported accuracy. Only four seeds and one fixed 198-image split were tested, so smaller effects cannot be ruled out.

## Prediction and webcam demo

```bash
python -m src.predict path/to/cropped_face.jpg                           # one image, top-3 classes
python -m src.predict face.jpg --config configs/rafdb.yaml --protocol paper
python -m src.webcam_demo                                                # live webcam, press q to quit
python -m src.webcam_demo --source video.mp4                             # or a video file
```

On macOS the first run asks permission for your terminal app to use the camera (System Settings, Privacy & Security, Camera).

**Pipeline** (`src/webcam_demo.py`): camera frame → OpenCV Haar cascade finds faces → crop the largest → grayscale → resize to the model's input (`cv2.INTER_AREA`) → divide by 255 → CNN → softmax → label and confidence drawn on the video, plus a bar per class and the frame rate. Predictions are averaged over the last 5 frames so the label does not flicker, and only the largest face is classified.

**Default model: FER2013** (set at the top of `src/predict.py`). Its training images are small in-the-wild grayscale faces, the closest match to a webcam crop, and it has a Neutral class, which CK+ lacks. CK+ is posed, frontal lab data and RAF-DB is the alternative via `--config configs/rafdb.yaml`. This choice is reasoned from the data, not yet validated live, so try both models on yourself.

**Checks done without a camera:**
- `predict.py`'s preprocessing gives the same class as the training-time evaluation for 200 of 200 FER2013 test images, so the demo feeds the model what it was trained on.
- Haar face detection found the face in 100/100 padded CK+ stills but only 73/100 FER2013 and 71/100 RAF-DB stills (small, noisy crops), so expect missed detections in poor light or at an angle.
- The softmax confidence shown is not a calibrated probability; a model can be confident and wrong.
- Frame rate on live video has not been measured yet.

## Differences from the original code

What the official notebooks do, what this repository does, and why. Everything marked *verified* was checked in the code or measured here.

| # | Original notebooks | This repository |
|---|---|---|
| 1 | The **test set is passed as `validation_data`**, so early stopping, LR reduction and `restore_best_weights` use it (verified in all three notebooks). | `--protocol paper` keeps this exactly. `--protocol clean` monitors a stratified 10% slice of the training data and touches the test set once. Measured effect: negligible (see Results). |
| 2 | `validation_split=0.1` with `subset='training'` silently **never uses 10% of the training images** (CK+ 783 → 708, FER2013 28,709 → 25,841, RAF-DB 12,271 → 11,046). | Kept in both protocols so the two train on identical images; the clean protocol reads that unused slice as validation. |
| 3 | **No seeds** anywhere, including the CK+ 80/20 split (`np.random.shuffle` on `os.listdir()` order). | Seed 42 for Python, NumPy, TensorFlow, the generators and the CK+ split (files sorted first). `--seed N` varies training only. GPU kernels are not guaranteed bit-exact, so reruns can differ slightly. |
| 4 | An `ExponentialDecay` schedule is defined but **never used**; `compile()` gets `Adam(learning_rate=0.001)`. | Constant-LR Adam, as actually trained. |
| 5 | `ReduceLROnPlateau(factor=0.001)` divides the LR by 1000 at each plateau (1e-3 → 1e-6 → 1e-9...), which freezes training (visible in the notebooks' own logs). | Kept unchanged (paper mode must be faithful); documented and shown in the logs. Typical values would be 0.1 to 0.5. |
| 6 | **FER2013 label list is shifted:** `label_map` says Angry, Disgust, Fear, Happy, Sad, Surprise, Neutral but Keras' folder order is angry, disgust, fear, happy, **neutral, sad, surprise**. The paper's rows for Sad, Surprise and Neutral belong to Neutral, Sad and Surprise (verified numerically against the paper's Table 4). | Class order comes from the config and `check_class_order` **stops the run** if Keras disagrees. |
| 7 | **RAF-DB labels are wrong for 4 of 7 classes.** Folders `1`–`7` are Surprise, Fear, Disgust, Happy, Sad, Angry, Neutral (checked against the published class totals and sample faces); the notebook says Angry, Disgust, Fear, Happy, Sad, Surprise, Neutral. | Correct names throughout (`results/rafdb/label_check.png`). Overall accuracy is unaffected. |
| 8 | CK+ images are split at random per image, but every sequence has **3 near-identical frames**: 91% of test images have a sibling in training, 98% share a subject. | Same image-level split for comparability, with the leakage measured and reported (`results/ck/split_report.json`). A subject-wise split is future work. |
| 9 | Accuracy is `model.evaluate()`'s value, whose progress bar disagrees with the printed number in the notebooks (e.g. 0.92 vs 0.95). | Accuracy is computed from the predictions with scikit-learn, so every number matches the confusion matrix. |
| 10 | Paper text vs code: RAF-DB "colour" (code loads grayscale); "zero-mean normalisation" (code only divides by 255); background removal, label cleaning and class balancing (none in the code); CK+ "8 classes" (7 in the data); FER2013 test size 3,589 in Table 2 (the dataset's test folder has 7,178). | Follows the code, not the text. |
| 11 | Claims an analysis of which facial movements drive the CNN's decisions, and real-time suitability. | Neither is in the released code, so neither is reproduced. The webcam demo reports frames per second but real-time HRI suitability is not evaluated. |
| 12 | Three Keras notebooks; Intel i7 CPU; TensorFlow 2.18.0, Python 3.12 (paper Table 3). | One configurable package (`configs/`, `src/`), Apple GPU, TensorFlow 2.18.1, Keras 3.8.0, Python 3.11. Parameter counts equal the notebooks' exactly (7,057,351 / 2,907,984 / 9,985,872). |

**Added here:** the clean protocol, the multi-seed experiment, full evaluation outputs (curves, confusion matrices in counts and normalised form, classification reports, one-vs-rest ROC, prediction grids, `run_info.json`), single-image prediction and the webcam demo.

**Limitations.** One seed for RAF-DB and FER2013 (CK+ has four); a fixed CK+ split; the CK+ test set is leaky under both protocols; no latency or real-time evaluation on a robot; confidences are uncalibrated softmax scores.
